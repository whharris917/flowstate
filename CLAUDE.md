# flowstate

A first-person factory-building simulation game set aboard a massive starship. The player builds a pharmaceutical plant from raw materials and bare bulkheads, one sensor, relay, and wire at a time, guided by an AI that can only perceive what the player instruments.

**Read `docs/GDD.md` before doing any design or implementation work.** It is the single source of truth for vision, story, world, systems, progression, and build order.

## Roles
- The human is the **creative director**. They set vision, review builds, and report what they saw. They do not write code and should not be asked to.
- Claude is the **entire development team**: architecture, code, scenes, tools, tests, docs. Make decisions, explain them briefly, and ask only when a choice is genuinely creative rather than technical.
- The director cannot see Claude's screen. Claude CAN see rendered output when needed: run a probe scene windowed (a real window briefly appears) that screenshots the viewport to `user://*.png` and read the PNG (`%APPDATA%\Godot\app_userdata\flowstate\`) — see `game/world/hud_probe.gd`. Use this to verify visual/UI work instead of guessing. Claude must also run Godot headlessly (see Environment) before every delivery: `--import` to catch parse errors, then a `--quit-after 600` smoke run to catch runtime errors and read the kernel self-check. Deliver things the director can open and press play, then ask for a build report ("what did you see, what felt wrong").

## Architecture rules
- **The sim is data plus a tick.** Simulation logic lives in plain classes with declared inputs/outputs and `tick(dt)`. Nodes only render and take input. No game logic in `_process`.
- Two layers: **process** (material streams) and **signal** (24 V discrete, 4–20 mA analog, later fieldbus). Components bridge them.
- **Rich streams between units, deliberately simple equations inside them** (director's call, 2026-08-31). Material moves as a `Stream`: rate, temperature, composition (species fractions) and a suspended-solids fraction, conserved when streams merge, split and blend into a vessel. But the *inside* of a unit is a handful of algebraic and first-order relations — fractional conversion, a lumped energy balance, a split ratio. No discretized transport, no VLE, no film coefficients, ever. The two decisions reinforce each other: a unit you can describe in five equations is a unit you can put on a page in-game. Internals may be animated freely, but always off real state.
- Two material port kinds keep the old type safety: `PROCESS_STREAM` is material actually being pushed (a pump discharge); `PROCESS_SUPPLY` is material offered at a nozzle for a consumer to pull (a tank outlet). They cannot be wired to each other, so two vessels need a transfer pump between them — the same answer a real plant gives. `PROCESS_FLOW` survives only as the scalar draw-demand wire; `PROCESS_LEVEL` only as an instrument tap.
- **The equipment library is generated, never hand-copied.** `EquipmentSpec` declarations live on each Python class beside the `tick()` that implements them and are the only copy of the equations; `tools/generate_library.py` writes `game/sim/sim_library_data.gd`. Port tables are never authored at all — both `sim/library.py` and `sim_library.gd` read them off a live constructed component, so a page cannot describe I/O the code does not have. `tests/test_library.py` fails if a real port lacks a meaning, a meaning names a dead port, a constructor param is undocumented, or a page states no assumptions. Re-run the generator after touching any SPEC.
- Fixed-rate deterministic tick. No frame-rate dependence.
- Every visual object in the world is backed by a sim record. No decorative equipment.
- **The historian is first-class.** Every sim variable is a tag, sampled every tick into a time-series record. All displays — trend pages, HMIs, gauges — read from the historian or live sim state. Displayed data is never faked, smoothed, or hand-tuned; it must be an accurate reflection of simulated process conditions, as if read from a plant historian (PI / DeltaV Process History View).
- **Every feature ships visual, as a GUI.** A delivery is not done until the director can *see* the process behave: during the Python phase, a live browser GUI (stdlib http server + HTML/JS) with operator graphics and trends of the real historized data; in-game HMI trends later. Include how to launch it.
- Save/load serializes the sim graph. Keep it working from the first playable.
- Placeholder art only (boxes, capsules, flat color) until systems are proven.
- Prototype new mechanics in `sim/` (Python) first when it is cheaper to validate there; port to GDScript once the design is settled.

## Conventions
- GDScript: static typing everywhere (`var level: float = 0.0`), snake_case, one class per file, `class_name` on sim classes.
- Python: 3.11, type hints, pytest, no heavy dependencies.
- Commit small, descriptive, and often. Never commit `.venv/` or `game/.godot/`.
- When delivering a build, end with: what changed, how to test it in Godot, and what to look for.
- **New equipment type checklist** (the standard rhythm, in order): (1) Python class in `sim/` + pytest; (2) an `EquipmentSpec` on that class — summary, a meaning for **every** port, equations, params, and an honest assumptions list; (3) GD mirror in `game/sim/` with `state_dict`/`apply_state` that round-trips its `contents` stream; (4) view in `game/components/` with describe()/use(), sim-edge audio, and any plumes; (5) `plant_factory.gd` — catalog entry, FOOTPRINTS, Y_OFFSETS, PORT_ANCHORS (`{"pos","dir"}` per port; unanchored ports get an ugly default marker), make_record arm, make_view arm, FLOW_OUTLETS/FLOW_INLETS if it supplies/consumes material; (6) `plant.gd` — place() setup arm and `_params_for` if it has constructor params (else save/load loses them); (7) `asset_preview.gd` setup arm; (8) `tools/generate_library.py` — add the type id to TYPE_IDS, then re-run it; (9) commission one in `showcase.gd` (wired, powered, running); (10) full gauntlet: pytest, `--import`, both-world smoke runs, showcase probe + library probe, and read the screenshots.
- Build pages are capped at 9 entries (number-key selection). Adding a page means touching `_catalog()`, `_is_equipment_page()`, `page_names` and the `% N` wrap in `build_controller.gd` — all four, or the pages silently misalign.

See "Build order" in `docs/GDD.md`. Step 1 (Python kernel + live GUI demo) is done. Step 2 (Godot engine foundations) is in progress: first playable exists — FPS controller, look-and-interact, the step-1 plant in 3D on the GDScript kernel port, in-world HMI trend, save/load (F5/F9). Grid placement and player-made connections are done, including placeable structure (columns/beams/walls/decks/doors/windows/stairs/catwalks/railings, Tab pages) and the support rule: routed runs may not span more than 3 m unsupported (SupportCheck, engine-side geometry — the kernel stays geometry-free), clamp brackets render where runs are carried, unsupported runs flag alarm-red, X removes a run or structure. Standalone pipe/conduit/tray runs are placeable ahead of equipment and count as support (trays carry conduit). Runs take ASME service colors + line labels (E), signs are placeable/editable.

The control tier is in (kernel-first, Python `sim/control.py` + GD mirrors): PLC (di/do/ai/ao channels, memories, TON timers, scanned validated ladder program), PID (anti-windup, bumpless A/M), control valve, terminal blocks, mains feeder / PSU with POWER port kind + voltage-class specs (mismatches refused; pumps/reboiler/PLC genuinely dead unpowered). Control cabinets start as EMPTY enclosures with bare DIN rails; the cabinet editor (floating ✎ EDIT button when the door is open) places modules — PSU, one PLC CPU, I/O cards that gate PLC channel banks, relays, terminal strips — and lands internal wiring as hidden kernel wires; the 3D interior renders the layout, field wires land on flank markers, and the ladder editor edits the program with live power flow. Right-click any device for its I/O menu (declared ports, kinds, voltage specs, live values) to start/finish routed connections. Headless gauntlet is four checks: kernel, control (PID + ladder), build-api (incl. cabinet field->PLC->relay->field traversal and unpowered-rack refusal), support. Engine choice was re-confirmed with the director on 2026-08-29 (Unity considered, Godot chosen).

The process tier is in (kernel-first, Python `sim/` + GD mirrors in `game/sim/`, 177 pytest): Source (a *species* header — this is where each material enters the plant) / Drain (rate-limited, totalizing, and totalizing **product lost to sewer** separately), steam generator (real steam at a saturation temperature that tracks header pressure), heat exchanger (heats its stream, cannot exceed the steam temperature, duty recomputed from the rise actually achieved, everything admitted condenses), jacketed stirred reactor (A + B -> product + impurity with volume conserved; needs 60–100 °C AND a powered agitator; **impurity yield rises with temperature**, so heat buys rate and spends selectivity; clamped at the contents' bubble point with boil-off out a vapor nozzle), crystallizer (supersaturation against a linear solubility curve, reversible, jacket limited by coolant temperature), centrifuge (splits crystals from mother liquor on the phase **actually present** — its old purity_in wire is gone), cake dryer (energy balance against a latent heat; evaporates the most volatile liquid first, so it concentrates impurity as surely as product), solvent recovery still (per-species split about a cut temperature, capped by boilup — the unit that closes the recycle), cyclic vacuum lock, and a vial filler/capper isolator that records **what actually went into the vials**. **Facade flow pairing**: one player pipe from a supplier "outlet" to a consumer "inlet" expands into a material wire plus a metered draw wire (`PlantFactory.FLOW_OUTLETS`/`FLOW_INLETS`); "draw" ports are hidden from menus/markers. Pulling a run removes both wires — removing only one leaves a pump sucking on a tank and discharging onto the floor. User-facing terminology is strictly inlet/outlet (director's call — never "suction", "battery limit", "in_flow"). Tanks are opaque with three sight-glass strips and movable flanged nozzles (G-grab in connect mode; E resizes height/diameter); all fittings are attached stubs/junction boxes (never floating markers), and pipes leave along the fitting axis (0.35 m stub in `PipeRoute.routed`) before elbowing. Seven build pages (Tab): EQUIPMENT, SEPARATION, INSTRUMENTS, STRUCTURE, ROUTING & SIGNS, CONTROL, UTILITIES.

**Species and composition.** `sim/species.py` / `sim_species.gd` define six species (water, solvent, reagent A, reagent B, product, impurity) with only the properties some equation consults: cp, boiling point, and a linear solubility curve. Everything is on a 1 L = 1 kg aqueous basis, so mass and volume fractions are the same number and nothing carries a density. Composition is historized: every stream port fans out into `.flow`, `.temp`, `.solids` and a `.x_<species>` tag, so nothing a display shows is inferred. New instruments fall out of this for free — an inline temperature gauge and a purity analyser.

**The equipment library (L).** Every placeable type has a page: what it is, its real I/O with a sentence per port, the governing equations, what you size when you place it, the historian tags it contributes, and a blunt "WHAT THIS MODEL DOES NOT DO" section. The exchanger admits it has no LMTD; the still admits it has no trays or reflux ratio; the pump admits it has no pump curve. `world/library_probe.tscn` audits every page against the live records.

**Sensory layer (director's favorite feature — maintain it on everything new).** Every sound and visual effect derives from a real sim state edge, never a decoration timer: `EquipmentAudio.make()` loops (motors, boiler rumble, steam hiss, mains buzz) driven by `set_running(real_state)`; `EquipmentAudio.play_once()` one-shots on edges (valve stem travel + seat clunks, contactor clunks on start/stop, relay clicks — muffled inside closed cabinets, float-switch trip beeps, tank/reactor high-level annunciators, reaching-temperature and purity-milestone chimes, steam-trap discharges whose interval tracks real header pressure, vacuum-lock vent blasts, vial-machine servo/fill/cap sounds); `VaporPlume` particles throttled by state (boiler stack, column vent) or puffed per event (lock vents). The reactor sight glass lerps amber->green from live purity. All audio is generated procedurally by `tools/generate_audio.py` (deterministic, stdlib) — regenerate rather than hand-edit WAVs.

Sandbox showcase (`world/showcase.gd`, built by `sandbox.gd`): pipe rack PR-1, Unit 100 PID level loop, MCC room with a module-by-module cabinet running a batch tank on ladder logic + TON, and **Unit 300 — the complete synthesis train with a closed recycle**: reagent + recycled-solvent headers -> pumps -> boiler-fired HX preheat and duty -> reactor -> transfer pump -> crystallizer under a real temperature loop (TIC-303, direct acting, so its gains are negative) -> centrifuge -> cake hopper -> dryer -> product silo -> vial filler with a purity analyser on the fill line; mother liquor -> liquor tank -> recovery still -> **distillate back to the solvent tank and round again**, bottoms to a totalizing drain. Duties come from real sources: an exchanger for the reactor, hand controllers (HIC-305/307, PID in manual with a kW output range) for the dryer and reboiler. Commissioned seeding (warm charged reactor, product-rich crystallizer heel, recovered-solvent inventory) is deliberate so the loop is visibly working within a minute. `world/showcase_probe.tscn` (windowed) screenshots six vantages, prints honest live state, **soaks the kernel 20 simulated minutes and reports the material balance around the whole unit** (currently 99.9 % closed), and names any unsupported runs — run it after showcase changes and read both the numbers and the screenshots.
